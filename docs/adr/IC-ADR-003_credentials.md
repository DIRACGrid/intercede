# IC-ADR-003: Backend credentials: typed, declared, supplied by a provider

## Metadata

- **Created By:** Alexandre Boyer
- **Date:** 2026-07-03
- **Status:** Draft
- **Decision Maker(s):** Federico Stagni, Christophe Haen, Chris Burr
- **Stakeholders:** interCEde backend implementers; DIRAC/DiracX SiteDirector and PushJobAgent maintainers; DiracX token-issuance maintainers; site and VO operators
- **Depends on:** IC-ADR-001 (contract shape, lifecycle, public API and internals)

> **Scope, and how to read this.** This ADR sets a direction, like IC-ADR-001. It decides how every secret a backend needs in order to reach its resource is typed, declared, supplied, refreshed and written to disk. That covers bearer tokens, X.509 proxies and SSH secrets. It does not decide token issuance, it does not decide renewal of the *payload's* own credentials, and it does not fix the exact model fields, which are implementation.
>
> It does not cover the per-job secret carried by a submitted entity. That travels with the submission rather than with the channel, and it is `CopyVars` in IC-ADR-001 §2.1.

## Abstract

Backend authentication is on the critical path for the grid CE backends, and it has to work the same way for a batch cluster reached over SSH. This ADR sets out three pieces:

1. **Typed, immutable credential values.** `BearerToken`, `X509Proxy`, `SSHPrivateKey` and `SSHPassword`, sharing one base and grouped in a `CredentialSet`.
2. **Requirements the backend computes and keeps to itself.** A `CredentialRequirements` value says which resource is asking, which kinds are needed together, and which scopes a token needs. It is derived from the backend's resolved configuration and is never exposed on the backend.
3. **Provider-based supply.** A backend pulls a fresh `CredentialSet` from a caller-supplied `CredentialProvider` when its own is missing or close to expiry. The provider is an async context manager owned by the consumer. So the mechanics of freshness live in one place, while issuance and renewal policy stays entirely with the consumer.

Writing credentials to disk, and injecting them into the environment for backends that drive command-line tools, is internal. interCEde stores no secret and defines no settings.

## Motivation

### What we have to support

1. **A grid CE that needs two credentials at once.** One CE takes a bearer token for the channel and can be configured to include an X.509 proxy alongside it. Another needs the token for the channel and a proxy in the submit description, because the site reads VOMS attributes from it for its own accounting. Neither can be dropped today. Both are expected to become token-only once sites account on token claims, so the model has to make that a configuration change rather than an API change.
2. **A batch cluster reached over SSH from a pod.** The secret is a private key or a password. Neither has an audience, neither expires, and the key cannot be assumed to sit on the filesystem of whichever pod happens to be running.
3. **A credential that expires in the middle of a cycle.** A submission task runs for a while and a token does not last forever. Exactly one piece of code should notice and refresh, rather than every caller that touches a backend.
4. **A token scoped to one operation.** Submission, polling and cancellation are separate tasks, so a polling task should carry a read scope and nothing that would let it submit.
5. **The integration stacks, with no issuing service at all.** IC-ADR-002 creates throwaway credentials for each run. The same machinery has to work when the source is a file on disk and nothing renews anything.
6. **Several VOs on one CE.** One backend instance serves one VO at one endpoint, so credentials never mix between VOs, and a provider serving many backends has to know which one is asking.

### What the use cases require

- **Stateless and cache-safe.** Credentials must not be hidden mutable state on cached backends.
- **Policy belongs to the consumer.** Where credentials come from, and when they are renewed, is the consumer's decision. interCEde owns only the mechanics of asking at the right time and using the result correctly.
- **One supply path for every kind of secret.** Token, proxy and SSH backends use the same machinery, so there is one place to audit.
- **Nothing secret in configuration.** A credential is supplied at run time, never read from a configuration system or from a file that ships with the deployment.
- **Nothing secret in a public attribute.** What a backend needs, and what it currently holds, are neither readable nor writable from outside the backend.
- **Testable in containers.** The model has to work with per-run credentials generated by the test stacks.

## Specification

### 1. Credential values

Immutable, typed values sharing one base. The base carries the expiry, because that is the one field the freshness check needs and every kind has it. Grid credentials expire. SSH secrets do not, so their `expires_at` is `None`, and a credential that never expires is never stale, which makes it a single provider call at first use.

Secret material uses pydantic's secret types, so a value cannot be printed by accident: this makes "never logged" a property of the type rather than a rule people have to remember.

```python
class Credential(BaseModel):
    model_config = ConfigDict(frozen=True)
    expires_at: datetime | None = None    # None means it never goes stale

class BearerToken(Credential):
    value: SecretStr                      # opaque to interCEde

class X509Proxy(Credential):
    pem: SecretBytes                      # private key and certificate chain together, which is
                                          # what the environment variable points at, and what a
                                          # delegation request is signed with

class SSHPrivateKey(Credential):
    pem: SecretBytes                      # the key itself, NOT a path on some host
    passphrase: SecretStr | None = None

class SSHPassword(Credential):
    value: SecretStr

class CredentialSet(BaseModel):           # what a provider returns
    model_config = ConfigDict(frozen=True)
    def get(self, kind: type[Credential]) -> Credential | None: ...
```

interCEde never inspects credential contents beyond the expiry. It parses a proxy into a certificate object only internally, for expiry and delegation, and the boundary type stays raw bytes.

`SSHPrivateKey` carries the key material rather than a path, on purpose. A path is only meaningful on the host that holds the file, and that host is a pod that can be rescheduled. The consumer reads the file once, wherever it is mounted, and passes the bytes.

`CredentialSet` returns a set rather than a single value because a backend can need more than one kind at the same time (Motivation 1). We expect that to stop being true, and the set is what lets it stop being true without changing the provider protocol.

### 2. Requirements: computed by the backend, and internal

```python
class CredentialRequirements(BaseModel):
    model_config = ConfigDict(frozen=True)
    resource: str                          # WHICH backend instance is asking: the endpoint it
                                           # talks to. For a token this is also the audience the
                                           # CE expects, in the form that CE expects it.
    kinds: frozenset[type[Credential]]     # needed TOGETHER, not a menu of alternatives
    scopes: frozenset[str] = frozenset()   # for token kinds, the scopes for THIS operation.
                                           # Empty for kinds that have no notion of scope.
```

A backend computes its requirements from its resolved configuration. There is one set per backend instance, because one instance maps to one endpoint.

**`resource` replaces a separate audience field.** A token's audience is the endpoint identity, written the way that CE expects it. A separate field would hold the same string twice and let the two disagree. So there is one field, and the backend produces the form its CE accepts. `resource` is also what lets one provider serve many sites: a provider shared across backends has to know which host it is answering for, and an SSH secret has no audience to carry that.

`scopes` stays token-specific, and is empty for kinds that have no notion of scope. Splitting the type per kind to avoid one empty field would push a union into every provider implementation for no gain.

Scopes are per operation: submission needs a create scope, status only a read scope, cancellation a cancel scope. Because the consumer splits those into separate tasks, each task drives one operation and pulls a token scoped to exactly that.

**The requirements are not a public attribute of the backend.** Nothing needs to read them. The backend passes them to `provider.get(...)` as an argument, so the consumer receives them exactly where it acts on them, inside its own provider. An attribute that can be read also invites one that gets written, which would put the site's authentication mode back into caller code. `CredentialRequirements` is therefore public only as the argument type of a method the consumer implements.

Two rules, both forced by the grid CEs:

- **`kinds` means "all of these, together".** Requirements describe the backend's active configuration, not a menu. A backend that can authenticate either way resolves that at configuration time: the site configuration picks the mode, and the requirements then name exactly the configured kinds. There is no runtime negotiation.
- **A required kind need not authenticate the channel.** One CE takes a proxy in the submit description purely so the site can read VOMS attributes from it, while the token authenticates the channel. The provider sees no difference, because it supplies the set. What each member is for is backend mechanics. When sites move to accounting on token claims, the requirement shrinks to token-only, and because requirements are data that is a configuration change rather than an API break.

### 3. Supply: a provider that the backend pulls from

```python
@runtime_checkable
class CredentialProvider(Protocol):
    async def get(self, requirements: CredentialRequirements) -> CredentialSet: ...
    async def __aenter__(self) -> Self: ...
    async def __aexit__(self, *exc_info) -> None: ...
```

**The provider is an async context manager**, for the same reason backends and transports are (IC-ADR-001 §3). A real provider holds resources: a session to a token service, a connection to a proxy store, or a file handle. A plain function cannot release them at a known point, and a provider that opens a session per call is wasteful when a backend calls it once per credential lifetime.

Ownership is the important half:

- **The consumer creates the provider and closes it.** interCEde never closes a provider, because it did not create it. One provider is normally shared by every backend a task drives, so its lifetime is the task's rather than any single backend's.
- **A trivial provider is still a context manager.** A static provider wrapping files or fixed values holds nothing, and closing it does nothing. That covers the integration stacks and any standalone use.

How supply works:

- The provider is passed to the registry alongside the backend configuration.
- **The backend pulls, and the consumer implements.** Before an operation, if the backend's current set is missing or within a freshness margin of expiry, it awaits `provider.get(...)`. The margin is a library default that a provider can raise, because delegation renewal wants more warning than a bare token does. A credential with no expiry is never stale. This happens in one place, inside the library. What the provider does behind `get` is consumer code.
- Provider calls are per backend, not per job. One credential authenticates the channel, not each submission. One backend instance serves one VO at one endpoint, so several VOs on one CE means several instances, each with its own provider.
- Failures raise the authentication branch of `InterCEdeError` as whole-operation failures. Per the partial-failure rule of IC-ADR-001 §3, an authentication failure is never a per-id outcome.

### 4. Materialisation

Backends that drive command-line tools, or that need files on disk, get internal helpers and never a public contract. Those helpers cover secure temporary files, in a private directory with restrictive modes, and environment injection for the tools that read credentials that way. They are scoped to the operation and cleaned up at a known point, and the backend's context-manager lifecycle is the outer boundary for that cleanup.

### 5. Delegation is backend mechanics

Where a CE supports proxy delegation, the whole exchange is internal to that backend. It builds the request, signs it with the provider-supplied proxy, uploads it, renews it before expiry, and reuses it across submissions while it is valid. The provider supplies the proxy and sees none of the rest.

### 6. SSH transport credentials

The SSH transport uses the same machinery as the grid CEs, and the split runs along one line: configuration describes the resource, and the provider supplies the secret.

- **Configuration, because it is not secret:** host, port, user, any jump host, timeouts, the known-hosts material, and which authentication mode the site uses.
- **From the provider, because it is secret:** the private key, or the password.

Three consequences:

- **The mode is chosen in configuration, not at runtime.** The site configuration says key or password, and the requirements then name exactly that kind. A transport does not try a key and fall back to a password.
- **Authenticating through a running agent needs no credential at all.** It is a mode in which the process holds no key material, so there is nothing for a provider to supply and no credential type for it. Prefer it where it is available.
- **Host key verification is not optional.** A key or password stops us reaching the wrong host by accident. Known-hosts verification stops the wrong host receiving the secret. That matters more once the secret comes from a central store.

### 7. Boundaries

- **Payload credentials are not backend credentials.** Renewing the credentials of the running payload belongs to the pilot and worker-node domain.
- **The per-job secret is not a backend credential either.** It authenticates the submitted entity to the workload management system, not interCEde to the resource. It is one value per submitted copy, it travels in the input sandbox, and it is `CopyVars.secrets` in IC-ADR-001 §2.1. The two models share one rule: secret material is staged as a file with restrictive modes and never written into a job description or an environment variable the site can read.
- **Issuance belongs to the consumer.** interCEde never holds refresh tokens, client secrets or certificate authority material. It asks a provider and uses what it gets.
- **Cloud provider keys go through the provider too.** They are secrets that reach an external service, so they are credential values like any other, not backend configuration.

### 8. Usage sketches (informative)

**(a) One provider, created once, shared by every backend.** The provider is built when the task starts and closed when it ends, so an individual backend never manages its lifetime:

```python
class DiracXPilotCredentials:                       # consumer-side; satisfies CredentialProvider
    def __init__(self, settings: CECredentialsSettings) -> None:
        self._settings = settings                   # constructed, nothing opened yet

    async def __aenter__(self) -> Self:
        self._tokens = await make_token_client(self._settings)   # one session for every backend
        return self

    async def __aexit__(self, *exc_info) -> None:
        await self._tokens.aclose()

    async def get(self, req: CredentialRequirements) -> CredentialSet:
        creds = []
        if BearerToken in req.kinds:                # scoped to what the backend asked for
            tok = await self._tokens.mint(audience=req.resource, scopes=req.scopes)
            creds.append(BearerToken(value=tok.value, expires_at=tok.expires_at))
        if X509Proxy in req.kinds:
            pem = await proxy_store.download(identity, lifetime=86400)
            creds.append(X509Proxy(pem=pem, expires_at=proxy_expiry(pem)))
        if SSHPrivateKey in req.kinds:              # one key per site, keyed by req.resource
            creds.append(SSHPrivateKey(pem=self._settings.key_for(req.resource)))
        return CredentialSet(creds)
```

The task opens it once, and each backend is used inside its own shorter-lived context:

```python
async with DiracXPilotCredentials(settings) as credentials:   # the task owns this
    for resource in resources:
        async with registry.backend(resource, credentials) as ce:
            await ce.submit(spec, copies)
            # before the operation the backend compared its cached set against its own
            # requirements and awaited credentials.get(...) only if it was stale. The
            # consumer saw the requirements only as the argument to its own get().
```

**(b) The integration stacks, with no issuing service.** The stacks write throwaway credentials into a shared volume, and a static provider wraps them. The same provider serves a token backend and an SSH one:

```python
provider = StaticCredentials(CredentialSet([
    BearerToken(value=read_token(), expires_at=None),
    SSHPrivateKey(pem=read_key()),
]))
async with provider:
    async with registry.backend(
        {"kind": "batch", "transport": "ssh", "scheduler": "slurm",
         "host": "batch.example.org"},              # not secret: stays in configuration
        provider,
    ) as ce:
        ...
```

## Rationale

- **Provider pull instead of setters on the backend.** A setter puts hidden state on an object the consumer caches, and it forces every caller to check freshness itself, which is how the same check ends up written more than once. A pull model puts the check in one place inside the library and leaves the source and the policy in consumer code, which is the same line IC-ADR-001 draws between mechanism and policy.
- **One model for grid and SSH secrets.** An SSH key is long-lived and looks like configuration, which makes it tempting to treat it as configuration. The consequence is a password sitting in a configuration system, a key path tied to one host's filesystem, and one backend family outside the audit surface. Folding it in costs two small models and removes the exception.
- **A shared base carrying the expiry.** Every kind has an expiry or explicitly has none, and the freshness check needs nothing else, so a base field is simpler than narrowing on a protocol at every check.
- **Internal requirements.** The consumer receives them where it can act on them, as the argument to its own `get`. Exposing them on the backend adds no capability and adds a surface that can be read and rebound.
- **A provider that is a context manager.** It holds real resources, and the consumer owning its lifetime avoids a backend closing something it did not create, which matters because one provider is shared by many backends.
- **Declared requirements rather than a flag somewhere in configuration.** A typed value can be tested, and it lets the conformance suite assert that the kinds a backend declares are the kinds it actually uses.
- **Immutability, and secret-typed fields.** Frozen values make a refresh a replacement rather than an in-place mutation, which is cache-safe under concurrent bulk operations. Secret-typed fields make "never logged" structural.

## Rejected Ideas

- **Setters that mutate credentials onto a live backend.** Hidden state on cached objects, and freshness policy spread across every caller.
- **Treating SSH keys and passwords as configuration.** It leaves a secret in a configuration system, ties a private key to one host's filesystem, and exempts a whole backend family from the audit surface.
- **A public attribute holding the backend's credential requirements.** Nothing needs to read it, and an attribute that can be read invites one that gets written.
- **A credential type for authenticating through an agent.** It would carry no secret material, so it would be a credential object with nothing in it. Choosing to use an agent is an authentication mode, which is configuration.
- **A separate audience field alongside the resource.** The two would hold the same string, and nothing good happens when they disagree.
- **Backend-driven issuance and refresh**, where the backend holds a refresh token or talks to the identity provider directly. It couples the library to one deployment's identity stack, embeds secrets in the library, and moves policy inside.
- **A provider that is a plain async function.** Simpler to write, and unable to own a session or release anything.
- **A credential store owned by interCEde.** interCEde is stateless (IC-ADR-001 §1), so caching beyond the current in-memory set belongs to the consumer.
